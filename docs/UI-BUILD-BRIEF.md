# UI build brief (read fully before writing any page)

Product: Townhall, meetings and elections for AOA/RWA/HOA societies (`docs/COMPLETION_PLAN.md` section 10 has the page map). Owner: non-technical, wants it **simple, idiot-proof, professional (not childish, not dull)**.

## Where things are
* Pages live in `apps/api/public/`. Every page is a tiny `index.html` (copy `public/index.html`) + one ES module in `public/assets/<page>.js`. **No inline script, no inline event handlers, no external requests** (the CSP forbids them), no framework, no build step.
* Use ONLY the shared kit: `public/assets/core.js` (read it all: `h()` DOM builder - text is never HTML, `api/get/post/put`, `explain/errorBox`, `radios/checks/field/stepBar/stageBar/wwh/modal/confirmBox/toast/busy`, `frame()`, `t()` for every user-visible English string) and `public/assets/townhall.css` (classes: `.card .btn .btn.gold .btn.ghost .btn.big .choice .steps .stages .wwh .msg .badge .table.t .code .working .tabs .timeline .grid .g2 .row .kv .nav`). Add page-specific CSS only in a `<style>` ... NOT allowed (CSP allows inline *styles* via style-src 'unsafe-inline', but prefer classes; short `style=""` attributes are fine). If you need a new shared class, append it to the END of `townhall.css` under a comment with your page name.
* Pattern to copy: `public/index.html` + `public/assets/home.js`.
* API contract: `docs/design/API.md` (read the WHOLE file, including addenda), `docs/UI-CONTRACT.md`, `docs/design/OWNER-DIRECTIVES-2026-10-23.md`. Real request/response shapes are in `apps/api/src/handler.ts` (search `route("POST", "/api/...`) and in the tests `apps/api/test/*.test.ts` and `apps/api/test/harness.ts` (shows a working create-event / roll / points / publish / start / vote sequence). The model shape for the public view is `ReportModel` in `packages/engine/src/model.ts`.
* A local server is already running: `http://localhost:8788` (real handler, in-memory data, TEST mode). `GET /dev/code?to=<email>` returns the last e-mailed 6-digit code (dev only). You may call the API with `curl` to learn shapes. Send header `x-device-id: <16+ letters/digits>` on writes. **Do not start browsers, Playwright, wrangler or any second server, and never run `bun test`** (laptop has ~1 GB free RAM; the lead runs tests and browser checks one at a time). Check your JS syntax with `bun build --no-bundle <file> --outfile /dev/null` only.
* Do not edit `apps/api/src/*`, `packages/*`, `migrations/*`. If you need an API change, write it in `docs/ui-api-requests.md` (append, one bullet each) and work around it.

## Owner standards (every page, no exceptions)
1. Plain words. Short sentences. No jargon (say "flat list", not "roll"; "check-in", not "attendance handshake"). Every user-visible string goes through `t("...")`.
2. Every screen starts with `wwh(who, what, how, why)` (the four-box strip: who you are here, what to do now, how, why it matters) unless the page is a pure public document.
3. Every error: show it with `errorBox(e, retryFn)` (server sentence + "How to fix"). Never show a bare code or a stack trace. Disabled buttons say why in a `.why-off` line.
4. Forms: radio buttons (`radios`) and check boxes (`checks`) wherever there are 2-6 choices; drop-downs only for long lists. Multi-part work is a **numbered step flow with Back / Next** (`stepBar`, `.nav`); on a phone use `.nav.sticky`.
5. Laptop layout is the default; phone layout is a separate design: for phone-first pages (voter, check-in station, hall screen) put `class="phone"` on `<main>` and design one decision per screen with big buttons (min 48 px).
6. Privacy: never show or store a full name/e-mail/phone on a public page. Full values only on the working screen of the person doing the check, only while doing it (see UI-CONTRACT "Working screens"). Never put passcodes, tokens or personal data in a URL query string (fragments `#...` are fine). Tokens live in `store` (sessionStorage) only. Never write "100%", "unhackable", "cheat-proof", "legally binding", "compliant". Use "tamper-evident", "verifiable", "designed around DPDP and GDPR".
7. Accessibility: labels on inputs, `role="alert"` on errors (errorBox does), visible focus (css does), tap targets >= 46 px, works with keyboard.
8. Resilience: if the network drops, keep what the user typed on screen, say so plainly, and offer "Try again". Poll live data every 5-10 s only where stated; stop polling when the tab is hidden.
9. Every page file you create must also be reachable by the dev server's routes (`/e/*`, `/v/*`, `/pay/*`, `/hall/*` rewrite to their `index.html`; other pages are directories `/name/index.html`).
10. Add a `data-test="..."` attribute on every primary button, input and key output element (stable hooks for the generated UI tests).

## Output
Only the files you were assigned. Finish by listing: files written, API routes used, anything you could not do, and requests for the lead. Keep the final report under 25 lines.

## Desk module contract (the Team Desk `/desk/` is assembled from modules written by different people)
`desk.js` (shell) signs the person in, loads the event, and renders a tab bar by role. Each tab is a module `public/assets/desk-<name>.js` with `export async function render(ctx, el)` that fills the element `el` (use `mount(el, ...)`). `ctx` = `{ eid, pid, token, roles: string[] /* from /api/auth/verify, e.g. ["organizer","host","attendance_officer"] */, model /* GET /api/events/:id -> .model (public, masked) */, progress /* same response .progress (8 setup steps, percent, phase, voting) */, priv /* GET /api/events/:id/private (staff view) or null for monitors */, refresh: async () => void /* reloads model/progress/priv then re-renders the current tab */, go: (tabName) => void, call: { get, post, put } /* same as core.js but token and event already applied: ctx.call.post("/points", body) hits /api/events/<eid>/points */ , schema /* GET /api/schema */ }`.
Tabs and owners: `setup` (desk-setup.js: the numbered 8-step wizard; step 5 "Helpers" calls `renderTeam` from `desk-team.js`), `team` (desk-team.js exports `renderTeam(ctx, el)`), `day` (desk-day.js: voting day control), `checkin` (desk-checkin.js: Attendance Monitor station), `end` (desk-end.js: end/postpone/cancel, pay link, recreate, erase, privacy requests, report e-mail), `record` (desk-record.js: chronology + who-did-what + audit trail view). A module must never assume another tab ran first, must work when `priv` is null (monitor) by simply showing a plain "This part is for the Organizer or Host." message, and must call `ctx.refresh()` after every successful write.
The handshake link the API returns is `/h/<token>`; the voter page `/v/index.html` also serves `/h/*` (dev server and Pages rewrite it).
