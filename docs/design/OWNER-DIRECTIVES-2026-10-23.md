# Owner directives of 2026-10-23 and how each one is built

These arrived while the build was running. Each row says what the owner asked, what exists now, and the honest limit. Evidence for every "built" item is in `docs/CHECKLIST.md`.

## 1. "100%" - what can and cannot honestly be promised
| Owner wording | What is built | Honest limit |
|---|---|---|
| 100% transparency | The complete log is public with no sign-in (`GET /api/events/:id/log`, the page, the PDF appendix). Every rule change, appointment, attendance mark, vote entry and result is an entry. Nobody can edit or delete (triggers). | Transparency covers what the system sees. It cannot see what happens in the room. |
| 100% secret ballot | Ballot box has no flat, no time, no IP, no device; random key; only aggregates and receipts published; audit rows never hold choices or receipts. Tested. | The server sees who is casting for the few milliseconds of a request; a malicious runtime could link them. Weighted ballots with unique weights are less anonymous (warning given). It is "secret from the stored and published data", not mathematically unconditional. |
| 100% data tracing | Every non-public-read request is audited twice (before and after) with IP address and device id; every log entry carries a fingerprint of them; every actor accepted the terms. | Device id is chosen by the browser (a determined person can change it); IP can be a shared or VPN address. Anonymous reads of public pages are not audited per request (flag `AUDIT_PUBLIC_READS=1` turns that on). Requests stopped by the first per-address rate limit are counted, not audited. |
| 100% per the voting laws and bye-laws of every HOA / AOA / RWA | Rule packs from the law study (7 jurisdictions) plus a custom pack for any society; the engine refuses to start with an unset required value, locks options the law fixes, freezes rules once voting opens, and prints a "Checked against the rules" table (notice, quorum, majority, proxy, secret ballot, eligibility, one vote per flat, terms) on every page and PDF. | **No software can promise legal conformity.** The packs carry a confidence level and a "have the society confirm against its own bye-laws" flag taken from the research; remote voting in India still needs a lawyer's opinion. The product records and checks; it does not give legal advice. |

## 2. Everything logged with IP address and device ID; terms ticked by everyone
* `GET /api/terms` returns the versioned terms (what is recorded, who can see it, secret-ballot statement, permanence, duties). Version `2026-10-23.1`, SHA-256 shown.
* The box must be ticked: by the Organizer when creating the event, by every Host / Attendance Officer on first sign-in, by every flat before its first ballot. Each tick is a `terms_accepted` log entry (public, no IP). A refused tick does not consume the passcode. Replay and the "Checked against the rules" table flag anyone who acted without it.
* Every request except anonymous public reads must carry `x-device-id` (16-64 letters/digits/-/_ made by the browser and kept in local storage); without it the request is refused (and the refusal is itself audited).
* `access_audit` (append-only, private, encrypted): a `request` row is written BEFORE the request is processed (if it cannot be written the request is refused: fail closed) and a `result` row after (status, log entry reached). Fields: time, event, route, actor kind and reference, IP, device id, browser (encrypted), blind indexes of IP and device (so the same address or device can be traced across rows without decrypting).
* Each public log entry carries `acc` = HMAC(server secret, event id, entry number, IP, device): a fingerprint that proves the entry is tied to a recorded request without publishing the address, and cannot be matched between entries by the public.
* Who sees what: public page - fingerprints only; Organizer/Host (`GET /api/events/:id/audit`) - IP shortened (`203.0.*.*`), device shortened; platform owner (`GET /api/super/events/:id/audit?reason=...`) - full values, only with a written reason, and the viewing becomes a public `platform_action: audit_read` entry.
* **Conflict recorded:** `PM-STANDARDS.md` section 2 says "raw IP is never stored". This directive from the owner supersedes it for audit purposes. Mitigations: encrypted at rest with the per-event key, never public, shortened for office-bearers, destroyed (unreadable) by crypto-shredding on a lawful erasure request. DPDP minimisation/consent wording is for the lawyer; the terms text must be reviewed before launch.

## 3. Prices (pay per event)
India: Rs 499 per meeting, Rs 1499 per election. Everywhere else: USD 5 per meeting, USD 15 per election. The society's country (`country`, two letters; defaults from the rule pack, required for the worldwide pack) selects the price; amounts are integers (paise/cents) with a currency; the page shows "Rs 499.00" or "USD 5.00". Payments stay TEST-only.

## 4. Final report as a PDF; legal document; published within 120 seconds
* `GET /api/r/:id/pdf`: A4 PDF built from the sealed report (deterministic: same bytes every time, fingerprint in `x-pdf-sha256`). It contains the identification (event id, rules in use), the four-milestone schedule, people with ids, attendance and quorum, every point with its id, ballot instruction, option ids, ticked/not-ticked counts, ranking and assignment, the "checked against the rules" table, the verification block (log head, key id, report file SHA-256, signature), a certification paragraph with signature blocks for the **Returning Officer / Presiding Officer, Chairperson and Secretary** plus a stamp box, the complete log as Appendix A and the receipt codes as Appendix B. Limit: standard PDF fonts, Latin text only (other scripts print as `?`; the HTML report has the full text). Whether a signed print is accepted as a legal document is for the society's lawyer / the authority; the PDF is built to be signed and submitted.
* Published within 120 seconds: the Host's close button publishes immediately (about 60 ms in the measured run); at the scheduled end the scheduler tick (`POST /api/internal/tick`, run every minute) closes the event and publishes the report automatically (checkbox `auto_publish`, on by default). Tested: tick at end + 30 s publishes; `published_ms - end <= 120000`. This depends on the owner-only scheduler calling the tick at least once a minute (deployment task).
* E-mail: the Organizer is e-mailed the PDF automatically at publication; `POST /api/events/:id/report/email` sends it to up to 10 addresses ("through our email engine": Resend adapter, local outbox stub, daily quota, second-provider slot). Every sending is a public `report_emailed` entry with masked recipients and the PDF fingerprint.

## 5. Nothing can be edited or deleted once published - not even by the owner
The log, every record table and the stored report refuse UPDATE and DELETE. Migration `0004` adds: after a report exists for an event, the database refuses new rows in the vote, attendance, roll, agenda, rule, option, role, point-state and status tables, refuses a second report, and accepts only log entries that record something *about* the published record (`clone_linked`, `anchor`, `platform_action`, `contacts_read`, `key_destroyed`, `report_emailed`, `vote_rejected`). The API refuses all staff actions on a closed event. Limit: a database administrator can still drop triggers; the signed chain, the sealed report file and the anchors then expose the change. The one deliberate exception is privacy erasure (destroying the key of the private store), which makes personal data unreadable but leaves the public record untouched; the owner may decide to disable it.

## 6. Unique ids
Event: 128-bit hex. Person: `p_` + 64 bits. Agenda point: `pt_` + 64 bits. Candidate / option of an election post: `c_` + 48 bits (a person standing for two posts gets a separate id per post). Ballot: its receipt hash. All ids are printed in the PDF and on the page; candidate ids stay stable when the Organizer amends the list before voting.

## 7. Ballot paper, check boxes, how many to vote for, election formats
* Design chosen by the Organizer per point (`design`): layout (list / cards / grid), columns, order (listed / shuffled per voter), accent colour, title, instruction, numbering, tick-box size. Validated; stored and published; frozen when the point opens. The default is phone-first (one column, large boxes); the UI must keep every layout single-column on a narrow screen.
* Every option is a check box. **Ticked = yes (selected), not ticked = no (not selected).** Voters send `marks` {id: true/false} (or the list of ticked ids). Results show for each option "ticked = yes" and "not ticked = no" counts.
* Number a voter may tick: `minChoices` and `maxChoices` set by the Organizer per point (0 allows a blank ballot).
* Election formats (`format`): **single_post** (separate election per post - President, VP ... - named by the Organizer, one point each), **ranked_posts** (one election for all posts: the highest vote gets the first post, the next the second ...; posts named in `seats`), **top_n** (selection of the first N, `topN`). Ties are shared ranks and are flagged for the Returning Officer. Numbers first; the "by rank" assignment is labelled "for the Returning Officer to confirm". All of it is chosen and may be amended until the point opens.

## 8. "The complete log is visible to everyone, who chose what"
The complete log is public. **Who chose what is public only for open votes** (checkbox "Record votes openly by flat"). For secret ballots it is not and cannot be, which is the "100% secret ballot" requirement; the two statements cannot both apply to the same ballot. Each point shows before voting whether it is open or secret. Owner to confirm this reading.
