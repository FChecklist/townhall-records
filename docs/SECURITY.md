# SECURITY (what is protected, how it is tested, what is not)

Full attacker-by-attacker table: `docs/design/THREAT-MODEL.md`. Every control marked there has a test, and `scripts/mutate.ts` shows each test failing when the code is broken (`docs/evidence/MUTATIONS-*.md`).

**Promise:** tamper-evident and independently verifiable. Not "cheat-proof".

## Controls in place
* Hash-chained, Ed25519-signed log, one per event; every entry signed; verifier in the engine and embedded in every page. A database trigger also refuses a gapped or forked chain.
* 23 record tables refuse UPDATE and DELETE by trigger; there is no DELETE route and no route that edits history. Corrections are new entries.
* 6-digit passcodes: generated by rejection sampling, stored only as HMAC(pepper, purpose|subject|event|code), single use, bound to one subject and one purpose, 15-minute expiry for login, 5 wrong tries lock for 15 minutes (even the right digits are then refused), constant-time compare with the same work on every path, one generic failure message, per-address / per-person / per-event rate limits, Turnstile on public forms (fails closed).
* Secret ballot: ledger (who voted) and ballot box (what) are separate; the box has a random primary key, no flat, no time, `WITHOUT ROWID`; only aggregates and receipts are published; voters get a receipt with a private nonce.
* Server clock decides voting windows. Rules freeze when a point opens (refusals are logged and shown). Roll and agenda freeze once voting starts.
* No one acts before verifying their e-mail, the Organizer included.
* Privacy at write time: masked values only in public tables and logs; the log refuses payloads containing a full e-mail or phone number; private contacts are AES-GCM encrypted under a per-event data key wrapped by a master secret; crypto-shredding destroys the key.
* Whole-file seal on the final report; the page can be re-verified offline from a saved copy.
* Super console: separate session kind, e-mail-code login (passkey to come), read-only plus logged support actions that also appear in the event's own log; cannot touch a live or closed event.
* Payments: TEST mode only; confirm and webhook routes exist only when `TEST_MODE=1`.

## Known limits (stated, not hidden)
1. The runtime sees who is voting for the duration of a request. We store no link, but a malicious runtime could. Secret ballots are secret from the published data and the stored tables.
2. A DB administrator can drop a trigger and rewrite rows; the chain and signatures then fail, but only someone who holds an anchor (the report, the Organizer's copy, the planned public GitHub anchor repo) can detect a rewritten *tail*. Publishing anchors off-platform is a deployment task (not done).
3. The signing key is the single trust root. Its rotation procedure and secure storage are deployment decisions (owner).
4. The in-page "Verify" runs code from the same file; a forger could alter both. The page tells the reader to compare the file hash with the anchored one or use the published verifier.
5. Weighted secret ballots: a flat with a unique weight is identifiable from the box. The roll endpoint returns `anonymityWarning`; default advice is one flat one vote for elections.
6. Candidate names in an election are agenda text and therefore public. Organizers must have candidates' consent (owner/lawyer decision, see DECISIONS).
7. E-mail inbox takeover = identity takeover for staff. Passkeys for staff are not built.
8. Not done yet: WebAuthn for the super console, CSP/headers for the UI pages (the report route already sends a strict CSP), a penetration test, abuse monitoring dashboards, the officer-held-device flow for voters without a phone (UI task).
9. Replay-per-request reads the whole event log from D1 for every vote (about 700 rows for a 120-flat AGM): fine functionally, but costs D1 row reads; see PERF.

## Addendum 2026-10-23
* New controls: terms acceptance for everyone, mandatory device id, fail-closed access audit with IP and device (encrypted, append-only), per-entry fingerprint, shortened view for office-bearers, full view only for the owner with a reason and a public record of the viewing, publication freeze by database triggers, automatic publication at the scheduled end.
* New limits: the device id is chosen by the browser and can be changed by a determined person; IP addresses can be shared or masked; anonymous public reads are not audited one by one (switch `AUDIT_PUBLIC_READS`); the scheduler must call the tick at least once a minute for the 120-second promise; the PDF is Latin-only; "100%" claims cannot be met by software - see OWNER-DIRECTIVES section 1.
